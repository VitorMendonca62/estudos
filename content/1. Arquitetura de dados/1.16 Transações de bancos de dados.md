### 1.16 Transações de Bancos de Dados

Uma **Transação de Banco de Dados** é uma **unidade lógica de processamento** (LUW — _Logical Unit of Work_) que executa uma ou mais operações de leitura (SELECT) e escrita (INSERT, UPDATE, DELETE) em um Sistema Gerenciador de Banco de Dados (SGBD). Ela atua como um bloco indivisível: ou **todas** as operações internas são concluídas com sucesso e consolidadas, ou o banco é revertido ao seu estado original.
#### 1. Ciclo de Vida e Estados de uma Transação
Durante sua execução no SGBD, uma transação passa por um conjunto bem definido de estados controlados pelo **Gerenciador de Transações**:

```
    ┌────────────┐
    │  Ativa     │
    └─────┬──────┘
          │
          ├─────────────────────────────┐
          ▼                             ▼
    ┌────────────┐               ┌────────────┐
    │ Parcial-   │               │   Falha    │
    │ mente      │               └─────┬──────┘
    │ Confirmada │                     │
    └─────┬──────┘                     │
          │                            │
          ▼                            ▼
    ┌────────────┐               ┌────────────┐
    │ Confirmada │               │ Cancelada  │
    │ (Committed)│               │ (Aborted)  │
    └────────────┘               └────────────┘
```

1. **Ativa (_Active_):** Estado inicial enquanto as instruções SQL estão em execução.
2. **Parcialmente Confirmada (_Partially Committed_):** Acontece logo após a última operação SQL ser executada, mas antes de salvar os dados definitivamente no disco rígido.
3. **Confirmada (_Committed_):** A transação executou o comando `COMMIT` com sucesso. Suas alterações foram permanentemente salvas em disco (log de transações/WAL) e a transação é finalizada.
4. **Falha (_Failed_):** Ocorre quando uma instrução falha ou uma verificação de integridade/hardware é violada.
5. **Cancelada (_Aborted/Rolled Back_):** O SGBD executa o comando `ROLLBACK`, desfazendo qualquer alteração parcial com o auxílio do _Undo Log_ e retornando o banco ao estado anterior.
#### 2. Comandos de Controle Transacional (TCL)
O gerenciamento transacional em comandos SQL é conduzido pela linguagem **TCL** (_Transaction Control Language_):
- **`BEGIN TRANSACTION` / `START TRANSACTION`:** Marca o início explícito do bloco transacional.
- **`COMMIT`:** Confirma e efetiva de forma irreversível e permanente todas as alterações feitas no banco.
- **`ROLLBACK`:** Cancela a transação e desfaz todas as alterações realizadas desde o início do bloco ou até o último `SAVEPOINT`.
- **`SAVEPOINT`:** Define um ponto de controle intermediário dentro de uma transação longa, permitindo desfazimento parcial (`ROLLBACK TO savepoint_name`) sem cancelar toda a transação.
#### 3. Os Dois Pilares de Suporte: WAL e Logs de Transação
Para garantir que as transações mantenham a consistência física e lógica diante de travamentos, o SGBD utiliza o mecanismo de **Write-Ahead Logging (WAL)**:
- **Write-Ahead Logging (WAL):** Exige que qualquer alteração de dados seja gravada primeiro em um arquivo de log sequencial em disco (_Redo Log / Undo Log_) **antes** que as páginas de dados na memória (_Buffer Pool_) sejam descarregadas no disco principal.
- **Undo Log (Desfazer):** Guarda os valores antigos dos dados. É usado para aplicar o **`ROLLBACK`** em transações canceladas ou durante falhas de sistema para cancelar transações que estavam ativas (garante **Atomicidade**).
- **Redo Log (Refazer):** Guarda os novos valores dos dados. É utilizado pelo algoritmo de recuperação (_Recovery Manager_) após uma queda do servidor para refazer e consolidar alterações de transações que já haviam dado `COMMIT` mas não deram tempo de ser gravadas nas tabelas em disco (garante **Durabilidade**).
#### 4. Concorrência e Anomalias em Transações
Quando múltiplas transações são executadas concorrentemente no SGBD, podem ocorrer problemas de interferência que o **Isolamento** tenta resolver:
1. **Leitura Suja (_Dirty Read_):** A Transação A lê dados modificados pela Transação B que ainda não deu `COMMIT`. Se B der `ROLLBACK`, A lê um dado que "nunca existiu".
2. **Leitura Não-Repetível (_Non-Repeatable Read_):** A Transação A lê uma linha. A Transação B altera/deleta essa linha e dá `COMMIT`. Se A ler a mesma linha novamente, obterá valores diferentes ou ela terá desaparecido.
3. **Leitura Fantasma (_Phantom Read_):** A Transação A lê um conjunto de linhas com base em uma condição (ex.: `WHERE salario > 5000`). A Transação B insere novas linhas que atendem a essa condição e dá `COMMIT`. Ao refazer a consulta, surgem linhas "fantasmas" no resultado.
4. **Atualização Perdida (_Lost Update_):** Duas transações leem o mesmo registro e tentam atualizá-lo concorrentemente; a alteração efetuada por uma delas é sobrescrita pela outra sem a devida sincronização.
#### 5. Mecanismos de Controle de Concorrência
Os SGBDs implementam estratégias para gerenciar o acesso simultâneo aos mesmos dados:
##### A. Controle Pessimista (Bloqueios / _Locks_)
O SGBD assume que haverá conflitos e bloqueia o acesso aos recursos:
- **Bloqueio Compartilhado (Shared Lock - S):** Usado para operações de leitura. Permite que outras transações também leiam o mesmo dado, mas impede alterações.
- **Bloqueio Exclusivo (Exclusive Lock - X):** Usado para operações de escrita (INSERT, UPDATE, DELETE). Impede qualquer outra transação de ler ou alterar o recurso.
- **Protocolo de Bloqueio em Duas Fases (2PL - _Two-Phase Locking_):** Garante a _serializabilidade_ dividindo a transação em duas fases:
    1. _Fase de Crescimento (Growing Phase):_ A transação adquire bloqueios, mas não libera nenhum.
    2. _Fase de Encolhimento (Shrinking Phase):_ A transação libera bloqueios, mas não pode adquirir novos.
- **Deadlock (Impasse):** Situação de travamento mútuo em que duas ou mais transações ficam esperando indefinidamente por bloqueios mantidos umas pelas outras. O SGBD detecta esse ciclo e encerra uma das transações (vitimimização) para liberar os recursos.

##### B. Controle Otimista e MVCC
- **Multiversion Concurrency Control (MVCC):** Utilizado por SGBDs modernos (como PostgreSQL e Oracle). Em vez de travar leituras durante escritas, o SGBD mantém múltiplas versões históricas das linhas. Leores enxergam uma "foto" (_snapshot_) consistente do banco no momento em que a transação começou, permitindo que **leituras não bloqueiem escritas e escritas não bloqueiem leituras**.
#### 6. Quadro Comparativo: Níveis de Isolamento (ANSI SQL)
Ajustam o nível de rigor no controle concorrencial:

| **Nível de Isolamento** | **Leitura Suja?** | **Leitura Não-Repetível?** | **Leitura Fantasma?** | **Mecanismo Típico no SGBD**                                                       |
| ----------------------- | ----------------- | -------------------------- | --------------------- | ---------------------------------------------------------------------------------- |
| **READ UNCOMMITTED**    | **Permite**       | **Permite**                | **Permite**           | Sem bloqueios de leitura; lê rascunhos.                                            |
| **READ COMMITTED**      | Não               | **Permite**                | **Permite**           | Bloqueios curtos de leitura ou _snapshots_ por instrução SQL (MVCC).               |
| **REPEATABLE READ**     | Não               | Não                        | **Permite**           | Bloqueios mantidos até o `COMMIT` ou _snapshots_ por transação.                    |
| **SERIALIZABLE**        | Não               | Não                        | Não                   | Bloqueios de intervalo (_Range Locks_) ou SSI (_Serializable Snapshot Isolation_). |
