O **Modelo Dimensional** é uma técnica de modelagem de dados voltada especificamente para o suporte à tomada de decisão, análise de dados e sistemas **OLAP (On-Line Analytical Processing)**. Diferente do **Modelo Relacional Tradicional (ER/3FN)**, focado no processamento de transações **OLTP** com alta normalização, o modelo dimensional **sacrifica a normalização para priorizar a performance de leitura**, a simplicidade de uso em ferramentas de BI e a velocidade em consultas agregadas.

---

### 1. Pilares do Modelo Dimensional

O modelo dimensional estrutura os dados ao redor do processo de negócio por meio de duas estruturas centrais:
* **Tabelas Fato (Fact Tables):**
	* Focadas nos eventos ou transações de negócio.
	* Armazenam **Métricas/Medidas numéricas agregáveis** (ex.: `ValorVenda`, `Quantidade`, `Custo`).
	* Possuem uma **Chave Primária Composta**, formada pelas Chaves Estrangeiras (FKs) que apontam para todas as suas dimensões associadas.
	* Concentram o maior volume de dados (milhões/bilhões de tuplas).
	* **Granularidade (Grau de Detalhe):** Define exatamente o que uma linha da tabela fato representa (ex.: uma linha por item vendido em cada cupom fiscal).
* **Tabelas Dimensão (Dimension Tables):**
	* Fornecem o **contexto descritivo e qualitativo** em torno dos fatos (respostam a perguntas como *Quem? Onde? Quando? O quê?*).
	* Possuem menor volume de registros, porém muitas colunas textuais (atributos) altamente **desnormalizadas** (violando intencionalmente a 2FN/3FN).
	* A Chave Primária (PK) de uma dimensão costuma ser uma **Chave Substituta (Surrogate Key - SK)**, que é um inteiro sequencial gerado dinamicamente para gerenciar o histórico e dissociar o Data Warehouse das chaves operacionais dos sistemas de origem (Chaves Naturais/Negócio).

### 2. Arquiteturas de Esquemas Multidimensionais

A Cesgranrio costuma avaliar a diferenciação entre as estruturas físicas e lógicas multidimensionais:

| Esquema Dimensional                                                  | Características e Estrutura                                                                                                                                                       | Impacto em Performance / Junções                                                                                                                                            |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Star Schema (Esquema Estrela)**                                    | A tabela **fato** fica no centro, conectando-se **diretamente** às tabelas dimensão de nível único. As dimensões são totalmente **desnormalizadas**.                              | Otimizado para **leitura rápida**. Exige menos operações de `JOIN` em SQL, sendo o esquema recomendado para a maioria dos Data Warehouses.                                  |
| **Snowflake Schema (Floco de Neve)**                                 | Variação do Star Schema onde as tabelas dimensão são **parcialmente ou totalmente normalizadas** (ex.: a dimensão `Produto` conecta a `Subcategoria`, que conecta a `Categoria`). | **Reduz a redundância** no espaço de armazenamento, mas **aumenta a complexidade** e degrada a performance de leitura devido à necessidade de múltiplos `JOINs` encadeados. |
| **Fact Constellation Schema (Constelação de Fatos / Galaxy Schema)** | Possui **múltiplas tabelas fato** compartilhando tabelas dimensão em comum (Dimensões Conformes).                                                                                 | Essencial para cruzar dados de múltiplos processos de negócio na empresa (ex.: Fato `Vendas` e Fato `Estoque` compartilhando a dimensão `Produto` e `Tempo`).               |

### 3. Conceitos Avançados e Práticas Recomendadas

#### Dimensões de Mudança Lenta (Slowly Changing Dimensions - SCD)

Gerenciam como alterações nos atributos descritivos ao longo do tempo são tratadas na tabela dimensão:

* **SCD Tipo 1 (Sobrescrever):** O valor antigo é substituído pelo novo. Não mantém o histórico de alterações no DW.
* **SCD Tipo 2 (Nova Linha / Histórico Completo):** Uma nova linha é inserida na dimensão com uma nova *Surrogate Key* (SK), acompanhada de colunas de controle (ex.: `DataInicio`, `DataFim`, `FlagAtivo`). É a abordagem mais utilizada.
* **SCD Tipo 3 (Nova Coluna / Histórico Parcial):** Adiciona-se uma nova coluna para guardar o valor imediatamente anterior (ex.: `EnderAntigo` e `EnderAtual`).

#### Tipos de Tabelas Fato

* **Fato Transacional:** Cada linha registra um evento pontual no tempo (ex.: cada item vendido).
* **Fato de Instantâneo Periódico (Periodic Snapshot):** Salva o estado acumulado em intervalos de tempo fixos (ex.: saldo bancário ao fim de cada mês).
* **Fato de Instantâneo Acumulado (Accumulating Snapshot):** Linhas mapeiam processos que possuem etapas bem definidas e datas de início/fim (ex.: acompanhamento de um pedido do envio até a entrega).
* **Fato Sem Fato (Factless Fact Table):** Não contém métricas numéricas, servindo apenas para registrar a ocorrência/associação de eventos (ex.: registro de presença de alunos em aulas).

#### Operações Analíticas OLAP

Técnicas de navegação nos dados multidimensionais:

* **Roll-up:** Agregação de dados aumentando o nível de abstração (ex.: consolidar dados de *Meses* para *Anos*).
* **Drill-down:** O oposto de Roll-up; detalhamento do dado aumentando a especificidade (ex.: detalhar de *Anos* para *Meses*).
* **Slice:** Filtro que corta o cubo em uma única dimensão (ex.: analisar dados apenas para o ano `2026`).
* **Dice:** Subconjunto retido por filtro aplicado em duas ou mais dimensões (ex.: ano `2026` E região `Nordeste`).
* **Pivot (Rotate):** Rotação dos eixos do cubo multidimensional para alterar a perspectiva de visualização nos relatórios.

### Quadro Comparativo: Modelo Relacional vs. Modelo Dimensional

| Aspecto | Modelo Relacional (OLTP / 3FN) | Modelo Dimensional (OLAP / Kimball) |
| --- | --- | --- |
| **Objetivo Principal** | Operações diárias (Inserções, Alterações) com foco em integridade e transação. | Consultas analíticas pesadas e relatórios para tomada de decisão. |
| **Normalização** | Alta (Normalizado em 3FN para evitar redundâncias). | Baixa/Nula (Desnormalizado para otimizar a velocidade de consulta). |
| **Padrão de Escrita/Leitura** | Leitura e Escrita equilibradas (operações rápidas em poucos registros). | Predominantemente Leitura Massiva (com cargas em lote via ETL/ELT). |
| **Complexidade das Consultas** | Envolve muitos `JOINs` entre tabelas altamente fragmentadas. | Consultas simples e otimizadas (`JOINs` diretos entre Fato e Dimensões). |a Decomposição: Divide-se em duas tabelas: MEDICO_ESPECIALIDADE(Medico, Especialidade) e PACIENTE_MEDICO(Paciente, Medico).
