## 1. Conceito Central e Fluxo de Modelagem

A **Engenharia Reversa** (_Reverse Engineering_) é o processo inverso do fluxo tradicional de desenvolvimento de banco de dados. Enquanto a **Engenharia Avançada** (_Forward Engineering_) parte do abstrato em direção ao concreto ($\text{Negócio} \rightarrow \text{Conceitual} \rightarrow \text{Lógico} \rightarrow \text{Físico}$), a Engenharia Reversa analisa um **banco físico em execução, scripts DDL ou dicionários de dados** para reconstruir e extrair os **modelos lógico e conceitual**.

```
Engenharia Avançada (Forward):  [Negócio] ──> [Conceitual] ──> [Lógico] ──> [Físico / DDL]
Engenharia Reversa (Reverse):  [SGBD / DDL] ──> [Dicionário/Metadados] ──> [Lógico] ──> [Conceitual]
```
### 1.1 Principais Motivações de Negócio
- **Documentação de Sistemas Legados:** Atualizar diagramas de entidades e relacionamentos (DER) de sistemas antigos cujos bancos sofreram alterações diretas em produção sem atualização da documentação técnica.
- **Migração e Modernização:** Compreender a estrutura atual para refatorar ou migrar o banco para novas arquiteturas (ex.: migração para a Nuvem ou bancos NoSQL).
- **Integração de Sistemas:** Mapear esquemas heterogêneos para criar rotinas de ETL/ELT e _Data Warehouses_.
- **Governança de Dados:** Identificar e corrigir o _drift_ de esquema (divergência entre a documentação oficial e a estrutura real em execução no SGBD).
### 1.2 Funções Principais na Engenharia Reversa
- **Automação do Mapeamento Visual:** Conectam-se diretamente ao catálogo de metadados do SGBD ou leem arquivos de scripts DDL (`CREATE TABLE`) para gerar automaticamente os Diagramas Entidade-Relacionamento (DER).
- **Engenharia Redonda (_Round-Trip Engineering_):** Capacidade avançada de sincronização bidirecional. Permite que o analista realize alterações no modelo visual abstrato e as aplique no banco físico (_Forward_), ou leia alterações do banco físico e as atualize no diagrama visual (_Reverse_), mantendo a documentação e a produção sincronizadas.
## 2. O Papel das Ferramentas CASE (_Computer-Aided Software Engineering_)
As **ferramentas CASE** são softwares projetados para automatizar as tarefas do ciclo de vida do desenvolvimento de sistemas, sendo **fundamentais para a execução prática da engenharia reversa** em bancos de dados. É esperado que uma ferramenta CASE disponibilize funcionalidades de verificação quanto as regras que definem um modelo, ou que definem qualquer outro artefato do processo de desenvolvimento de software suportado por ela. Dessa forma, a ferramenta CASE é capaz de, em algum nivel, impedir ações por parte de usuários que levem a erros de modelagem.
### 2.1 Ferramentas CASE para modelagem de dados
- Ajuda na criação de Modelos Entidade Relacionamento
- Ajuda na criação de Modelos Relacionais
- Disponibilizar funcionalidades de criação automática de Dicionário de Dados
- Disponibilizar funcionalidades de criação de scripts de geração de banco de dados para tecnologias de SGBD's
- Possibita **engenharia reversa**
### 2.2 Exemplos de Ferramentas CASE de Mercado
- **erwin Data Modeler:** Uma das ferramentas corporativas mais difundidas para modelagem avançada, suporte a _Round-Trip Engineering_ e engenharia reversa multi-SGBD.
- **MySQL Workbench:** Ferramenta nativa do MySQL que permite realizar engenharia reversa diretamente a partir de conexões com o banco ou de scripts `.sql`.
- **Enterprise Architect:** Ferramenta CASE abrangente para modelagem UML e dados.
- **Oracle SQL Developer / Data Modeler:** Utilizada para extração e engenharia reversa no ecossistema Oracle.
## 3. Etapas Técnicas do Processo de Engenharia Reversa
1. **Extração de Metadados:**
    - Leitura do dicionário de dados do SGBD (ex.: visões do `INFORMATION_SCHEMA` em MySQL/PostgreSQL ou `ALL_TABLES`/`ALL_TAB_COLUMNS` no Oracle).
    - Mapeamento de tabelas, colunas, tipos de dados físicos e restrições (`PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `UNIQUE`, `NOT NULL`).
2. **Reconstrução do Modelo Lógico:**
    - Mapeamento direto de tabelas físicas para entidades/relações lógicas.
    - Mapeamento de colunas físicas para atributos lógicos.
    - Reconstrução das ligações entre entidades baseando-se nas restrições formais de Chaves Estrangeiras (FKs).
3. **Abstração para o Modelo Conceitual:**
    - **Tabelas Associativas:** Identificação de tabelas intermediárias contendo apenas duas FKs para derivar relacionamentos Muitos-para-Muitos ($M:N$) do modelo conceitual.
    - **Atributos Multivalorados:** Reconhecimento de tabelas auxiliares criadas exclusivamente para armazenar múltiplos valores de um atributo.
    - **Entidades Fracas e Especialização:** Identificação de tabelas cujas PKs dependem de FKs ou que implementam herança/especialização (ex.: tabelas conectadas via relacionamentos 1:1).
## 4. Desafios e Limitações Práticas (Foco Cesgranrio)
A Cesgranrio costuma explorar o fato de que a engenharia reversa via ferramentas CASE **não é 100% automatizada** e possui gargalos práticos importantes:
- **Ausência de Chaves Estrangeiras (FKs) Físicas:** Em muitos sistemas legados, a integridade referencial é controlada via código da aplicação e não declarada no SGBD. Sem FKs explícitas no banco físico, a ferramenta CASE **não consegue inferir os relacionamentos automaticamente**, exigindo mapeamento manual.
- **Perda de Semântica de Negócio:** Tabelas ou colunas com nomes genéricos ou abreviados (ex.: `TBL_AUX_01`, `CAMPO_A`) exigem análise heurística do analista de dados e inspeção dos dados reais (_Data Profiling_) para descobrir o significado do negócio.
- **Desnormalizações não Documentadas:** Tabelas desnormalizadas por razões de performance no nível físico tornam complexa a recuperação de um Diagrama Entidade-Relacionamento (DER) limpo e conceitualmente correto.
## 5. Quadro Resumo para Provas

| **Conceito**           | **Foco Principal / Pegadinha da Banca**                                                                               |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Objetivo Principal** | Reconstruir modelos abstratos (Lógico e Conceitual) a partir de estruturas físicas existentes no SGBD ou scripts DDL. |
| **Fonte Primária**     | Dicionários de Dados do SGBD (`INFORMATION_SCHEMA`), Scripts DDL e Código-fonte das aplicações.                       |
| **Ferramentas CASE**   | Softwares (ex.: erwin, MySQL Workbench) que automatizam a leitura do SGBD e geram os diagramas ER visualmente.        |
| **Engenharia Redonda** | Recurso da ferramenta CASE que permite a sincronização bidirecional das alterações (Forward + Reverse).               |
| **Principal Gargalo**  | A ausência de FKs explícitas no SGBD impede que ferramentas CASE identifiquem os relacionamentos entre tabelas.       |
