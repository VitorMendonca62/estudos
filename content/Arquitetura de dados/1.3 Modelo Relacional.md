O **Modelo Relacional** representa a fase intermediária da modelagem. Ele traduz as necessidades de negócio estruturadas no _Modelo Conceitual (DER)_ para o paradigma do SGBD que será utilizado.

Enquanto o conceitual se preocupa com _o quê_ armazenar, o modelo relacional se preocupa em **como os dados estarão estruturados**, definindo tabelas, colunas e restrições.  
## Modelo lógico
### 1. Principais Características
- **Dependência do Paradigma:** Depende do tipo de SGBD (ex.: Relacional, Orientado a Objetos, Colunar).
- **Independência de Software/SGBD Específico:** Não se preocupa com o software em si (se é Oracle, PostgreSQL ou SQL Server), nem com tipos de dados físicos do sistema ou armazenamento em disco.
- **Vocabulário Próprio:** Abandona-se o termo "Entidades e Relacionamentos" e passa-se a falar em **Tabelas (Relações), Colunas (Atributos), Linhas (Tuplas) e Chaves**.
### 2. Elementos Fundamentais do Modelo Relacional Lógico

- **Tabela (Relação):** Estrutura bidimensional composta por linhas e colunas.
- **Esquemas**: Um esquema define a estrutura ou o modelo de um banco de dados. Ele descreve como os dados são organizados, incluindo o nome da tabela, o nome do atributo, os tipos de dados e os relacionamentos entre as tabelas.
- **Tupla (Linha/Registro):** Cada ocorrência individual de dados em uma tabela.
- **Atributo (Coluna/Campo):** Cada característica/propriedade que a tabela armazena.
- **Chave Primária (PK - Primary Key):** Um atributo (ou conjunto de atributos) que identifica de maneira **única e exclusiva** uma linha na tabela. Não aceita valores nulos (`NOT NULL`) nem duplicados.
- **Chave Estrangeira (FK - Foreign Key):** Um atributo em uma tabela que aponta para a Chave Primária de outra tabela (ou da mesma), garantindo a **Integridade Referencial**.
- **Domínio (Tipo de dado):** O conjunto de valores válidos permitidos para um determinado atributo (ex.: valores permitidos para a coluna `Idade` sendo um `inteiro` ou `EstadoCivil`: 'Solteiro', 'Casado', 'Divorciado' ou `CPF` sendo um conjunto de números naturais com onze digitos ou `Titulo` sendo uma `STRING` ).

### 3. **Hierarquia e Restrição de Chaves**

Em banco de dados relacional, a identificação unívoca de uma tupla (linha) segue uma hierarquia matemática rigorosa:
- **Superchave:** Uma superchave é qualquer atributo ou combinação de atributos que consegue identificar uma linha de forma única em uma tabela. Não importa se ela tem dados sobrando ou desnecessários; se garante que não haverá duplicatas, é uma superchave.
    - _Exemplo:
	    - CPF) $\rightarrow$ É superchave (identifica o usuário).
		- `(CPF + Nome)` $\rightarrow$ É superchave (continua identificando, mesmo que o nome seja redundante).
	     - `(CPF + Email + Idade)` $\rightarrow$ Também é superchave (tem "gordura", mas ainda identifica).
 - -**Chave Candidata:** É uma **superchave mínima**. Ou seja, é um conjunto de atributos que identifica a tupla de forma única, mas se você remover qualquer atributo dele, ele perde a capacidade de identificação unívoca.
    - _Exemplo:_ 
	    - (CPF) $\rightarrow$ É Chave Candidata (se você tirar o CPF, não identifica nada).
	    - (Email) $\rightarrow$ É Chave Candidata (se for único no sistema, identifica por si só).
	    - -(CPF + Nome) $\rightarrow$ NÃO é Chave Candidata (é apenas superchave, pois se você remover o Nome, o CPF sozinho ainda funciona).
- Superchave Forte vs. Fraca (O Contexto de Entidades)
	Esse termo costuma aparecer quando comparamos **Entidades Fortes** e **Entidades Fracas**:
	- **Superchave (ou Chave) de Entidade Forte:** A entidade tem atributos próprios suficientes para formar superchaves sozinha.
    	_Exemplo:_ Em `Cliente`, o `CPF` por si só já é uma superchave.
	- **Superchave de Entidade Fraca:** A entidade fraca não tem atributos próprios suficientes para se identificar sozinha. Para formar uma superchave, ela precisa **combinar** seus próprios atributos (sua _chave parcial/discriminador_) com a **chave primária da entidade forte** à qual pertence.
		_Exemplo:_ Na entidade fraca `Dependente`, o atributo `numero_sequencial` (ex: 1, 2, 3) não identifica ninguém no sistema todo. A **superchave** do dependente será a combinação: `(CPF_do_Titular + numero_sequencial)`.
- **Chave Primária (PK):** É a **chave candidata escolhida pelo projetista** para ser o identificador principal da tabela no SGBD. Restrição estrita: não aceita valores nulos (`NOT NULL`) nem duplicados.

> **Resumo de Inclusão:** Todo subconjunto que é _Chave Primária_ $\subset$ é _Chave Candidata_ $\subset$ é _Superchave_.
### 4. Regras de Mapeamento: Do Modelo Conceitual para o Modelo Lógico

Esta é a parte **mais cobrada pela Cesgranrio em provas**. A banca ama exigir a conversão de um Diagrama Conceitual em Tabelas Lógicas:

#### A. Entidades Fortes $\rightarrow$ Tabelas

- Cada entidade forte do DER vira uma **tabela simples**.    
- Os atributos simples viram colunas e o atributo identificador vira a **Chave Primária (PK)**.
#### B. Relacionamentos 1:1 (Um para Um)

- **Como mapear:** A Chave Primária de uma das tabelas migra como **Chave Estrangeira (FK)** para a outra tabela.
- _Regra de Ouro:_ A chave deve migrar preferencialmente para a tabela que possui **participação total (obrigatória)** para evitar valores nulos.

#### C. Relacionamentos 1:N (Um para Muitos)
- **Como mapear:** A Chave Primária do lado **"1"** migra para a tabela do lado **"N"** como **Chave Estrangeira (FK)**.
- _Atenção:_ **NÃO** se cria uma nova tabela para relacionamentos 1:N no modelo relacional.

#### D. Relacionamentos N:M (Muitos para Muitos)
- **Como mapear:** É **OBRIGATÓRIO** criar uma **nova tabela** (chamada de _Tabela Associativa_, _Tabela de Junção_ ou _Intermediária_).
- A chave primária dessa nova tabela será a **combinação das Chaves Primárias das duas tabelas originais** (uma chave primária composta).
- Se o relacionamento conceitual possuir atributos próprios, eles vão para essa nova tabela.
    
#### E. Atributos Multivalorados
- **Como mapear:** Um atributo multivalorado (ex.: `Telefone`) **NÃO** pode ficar na tabela principal (pois violaria a Primeira Forma Normal - 1FN).
- **Solução:** Cria-se uma **nova tabela dedicada** para o atributo, contendo a FK da tabela principal + o valor do atributo.
#### F. Entidades Fracas
- Viram tabelas próprias, mas sua Chave Primária será composta por: `(Chave Primária da Entidade Forte proprietária + Seu Atributo Parcial/Discriminação)`.

### 5. Regras
#### 5.1 Implicitas:
1. **Integridade de Domínio:** Os valores de uma coluna devem respeitar o tipo e a faixa de valores permitidos (ex.: não inserir texto em campo de data).    
2. **Integridade de Identidade:** Nenhuma Chave Primária (PK) pode ser nula (`NULL`) nem conter valores duplicados.
3. **Integridate de chave**: É obrigatório que todas as tuplas em uma relação serem distintas, então deve haver um campo para que essas tuplas se diferenciem, para isso, deve ser usado, pelo menos, uma chave primária;
4. **Integridade Referencial:** Uma Chave Estrangeira (FK) só pode conter valores que **já existam** na Chave Primária (PK) da tabela referenciada, ou ser nula (quando a participação for opcional).
#### 5.2 Explicitas
São as restrições **definidas explicitamente pelo projetista/desenvolvedor** no momento em que cria o esquema do banco de dados (geralmente via código DDL). Elas complementam a estrutura básica do modelo para atender aos requisitos operacionais do sistema.
 - **`NOT NULL`:** Especifica expressamente que determinado atributo não-chave é de preenchimento obrigatório.
- **`UNIQUE`:** Garante que os valores de uma coluna não se repitam, criando chaves candidatas alternativas (ex.: o atributo `CPF` em uma tabela de clientes).
- **`CHECK`:** Aplica uma validação condicional customizada para valores de uma coluna (ex.: `CHECK (idade >= 18)` ou `CHECK (salario > 0)`).
- **`DEFAULT`:** Define um valor padrão caso nenhum valor seja inserido manualmente na coluna.
#### 5.3 Negócio
São as regras que **refletem o funcionamento e as políticas específicas da organização**, indo além do que o esquema estático do banco de dados consegue validar diretamente.
- **Conceito:** Representam condições do mundo real que não conseguem ser expressas apenas com declarações simples de `CHECK` ou `FOREIGN KEY`.
- **Implementação:** Costumam ser implementadas no banco por meio de **Gatilhos (`Triggers`)**, **Procedimentos Armazenados (`Stored Procedures`)**, ou diretamente no código da **aplicação**.
- **Exemplos:**
    - _"Um cliente não pode realizar um novo pedido se possuir faturas vencidas há mais de 30 dias."_
    - _"O limite de horas alocadas para um funcionário em um projeto não pode ultrapassar 44 horas semanais."_
#### 6. Notações do Modelo Lógico

No modelo lógico relacional, os esquemas são representados por notações textuais ou diagramáticas padronizadas:  

**1. Notação Textual (Esquema Relacional)**
É a forma mais comum em questões teóricas da Cesgranrio:
- O nome da tabela fica em maiúsculo.
- A **Chave Primária (PK)** é grifada/sublinhada (ou com `#`).
- A **Chave Estrangeira (FK)** vem indicada com itálico, asterisco `*` ou uma menção explícita no final.

> **Exemplo:**
> `DEPARTAMENTO` (CodDepto, NomeDepto)
> `FUNCIONARIO` (Matricula, Nome, CPF, _CodDepto_)
> _Onde `CodDepto` em `FUNCIONARIO` é FK para `DEPARTAMENTO(CodDepto)`._

**2. Diagrama de Relacionamento de Entidades Lógico (IDEF1X / Pé de Galinha - Crow's Foot)**

## Modelo físico
O **Modelo Físico** representa o nível mais baixo de abstração na modelagem de dados. Ele traduz a estrutura construída no modelo lógico diretamente para comandos executáveis de um **Sistema Gerenciador de Banco de Dados (SGBD) específico** (como PostgreSQL, Oracle, SQL Server ou MySQL).

Enquanto o modelo conceitual trata das regras de negócio e o modelo lógico define tabelas e relacionamentos, o modelo físico trata de **como os dados serão efetivamente gravados no disco, otimizados e gerenciados em memória pelo SGBD**.
### **1. Principais Características**
- **Dependência Total de Software (SGBD):** Diferente dos modelos anteriores, o físico é totalmente atrelado às sintaxes, limitações e particularidades do SGBD escolhido.
- **Tipagem de Dados Específica:** As colunas recebem tipos concretos aceitos pelo banco (ex.: `VARCHAR(100)`, `BIGINT`, `BOOLEAN`, `TIMESTAMP`).
- **Foco em Desempenho e Armazenamento:** É onde se aplicam técnicas de indexação, particionamento e ajuste fino (_tuning_).
- **Implementação via DDL:** O modelo físico ganha vida através do código SQL da **Linguagem de Definição de Dados (DDL)**.
### **2. Principais Elementos do Modelo Físico**
- **Script DDL (Data Definition Language):** Conjunto de comandos de criação e modificação de estruturas no banco.
    - `CREATE TABLE`: Criação física das tabelas, colunas, chaves primárias e estrangeiras.
    - `ALTER TABLE`: Modificação de estruturas já existentes.
    - `DROP TABLE`: Exclusão de tabelas.
- **Restrições (Constraints):** Mapeamento físico das regras de integridade:
    - `PRIMARY KEY`: Define a chave primária física.
    - `FOREIGN KEY`: Garante a integridade referencial.
    - `NOT NULL`: Impede valores ausentes.
    - `UNIQUE`: Garante que valores de uma coluna não se repitam.
    - `CHECK`: Valida condições lógicas para aceitar um dado (ex.: `CHECK (Idade >= 18)`).
- **Índices (Indexes):** Estruturas de dados auxiliares (como _B-Tree_ ou _Hash_) criadas para acelerar a busca e recuperação de informações em consultas `SELECT`.
- **Visões (Views):** Tabelas virtuais baseadas no resultado de uma consulta `SELECT`, usadas para simplificar consultas complexas e restringir acessos.
- **Procedimentos Armazenados e Gatilhos (Stored Procedures e Triggers):** Blocos de código SQL/PL-SQL armazenados no próprio SGBD para executar regras de negócio automaticamente diante de eventos como `INSERT`, `UPDATE` ou `DELETE`.
    
### **3. Otimização e Performance no Nível Físico**
A Cesgranrio explora com frequência itens ligados ao ajuste de performance do modelo físico (item 1.17 do edital):
- **Particionamento de Tabelas:** Divisão de uma tabela grande em pedaços menores (partições por intervalo de datas, listas ou hash) para acelerar a leitura e manutenção sem alterar a aplicação.
- **Tablespaces / Arquivos de Dados:** Definição em qual disco rígido ou arquivo do sistema operacional as tabelas e índices serão armazenados fisicamente.
- **Desnormalização Controlada:** Tecnica onde se quebra propositalmente a 3FN no modelo físico (introduzindo redundâncias ou colunas calculadas) para **reduzir a quantidade de `JOINs`** em consultas analíticas e melhorar a velocidade de leitura.
### **Exemplo Prático (Script DDL Físico)**
SQL

```
-- Exemplo de criação física em padrão PostgreSQL/ANSI SQL
CREATE TABLE departamento (
    cod_depto SERIAL PRIMARY KEY,
    nome_depto VARCHAR(100) NOT NULL
);

CREATE TABLE funcionario (
    matricula BIGINT PRIMARY KEY,
    nome VARCHAR(150) NOT NULL,
    cpf CHAR(11) UNIQUE NOT NULL,
    salario NUMERIC(10, 2) CHECK (salario > 0),
    cod_depto INT NOT NULL,
    CONSTRAINT fk_depto_funcionario 
        FOREIGN KEY (cod_depto) 
        REFERENCES departamento(cod_depto) 
        ON DELETE RESTRICT
);

-- Criação de um índice físico para acelerar buscas pelo CPF
CREATE INDEX idx_funcionario_cpf ON funcionario(cpf);
```
